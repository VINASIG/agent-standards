# QR intake consistency

The owner identified the same acquisition task with inconsistent presentation in QR Scanner and TOTP Generator. The scanner had its file and clipboard actions in a dashed card, with camera entry below. TOTP had a separate paste field and file/camera actions outside it. Maintaining two implementations allowed this drift.

WEB-010 now routes this task to [one shared intake contract](../../templates/web/qr-image-intake.md). This changes the shared acceptance documentation, not installer code, generated entrypoints or installed consumer runtime snapshots. The two affected consumers add local routing to their pinned common source. Existing decoder, TOTP, privacy, destructive-action and shared-chrome tests remain required.

## Shared source

The canonical Astro component and stylesheet are in [web-design-system at 06accd3](https://github.com/VINASIG/web-design-system/tree/06accd3c0831e9064812ea4b742ff40c6907cd18). Both consumers copy them verbatim and record that revision and the two SHA-256 digests in `docs/qr-intake-source.json`. Their regression tests check the named source files against these records. A GitHub API read of the immutable revision also matched both local source digests. No dependency, decoder version, artwork, font grant or installed runtime pin changes are part of this task.

One information surface contains a persistent label, a native paste target and ordered Choose image, Paste image and Scan with camera actions. Each product keeps its own decoded-payload validation, supported image types and secondary settings. TOTP retains its import disclosure and only accepts TOTP setup payloads. The design-system example explicitly disables acquisition rather than presenting inert buttons as working tools.

TOTP gains an explicit image clipboard button. It reads image items only after the button action, with revision checks before and after asynchronous delivery. Native paste and phone keyboard text delivery remain available. Denial keeps a local error and a working file/native-paste fallback. No clipboard polling, text/HTML clipboard read, upload endpoint or secret persistence is introduced. The privacy documentation was updated to describe this behavior.

## Validation and limits

- PASS: source, type, lint, format, build and license checks for both products and the design system; agent-standards source checks, 20 unit tests and build.
- PASS: the initial complete consumer suites exercised native file/paste/drop, decoder failure, camera lifecycle, revision cancellation, TOTP vectors, sharing, accessibility, preferences and destructive actions. TOTP passed 348 browser cases. Scanner passed 129 cases with its three pre-existing capability exclusions retained; this is not a claim that physical devices were exercised.
- The first enlarged-text screenshots exposed word fragmentation and a clipped placeholder despite a passing page-overflow check. These failures were retained. Bounded padding and two-line paste-field sizing fixed the observed problem, and the acceptance contract now requires opened images plus intact-word and placeholder measurements at 320 px and 200% text.
- PASS: each final consumer passed all 39 dedicated intake regressions across Chromium, Firefox and WebKit, both locales/themes, ten viewport widths, enlarged text and forced colors. Explicit clipboard success/denial, late delivery after clear and camera denial run without new skips or retries.
- PASS: 12 comparisons at the same 420 px intake width matched actual colors, typography, borders, spacing, icon dimensions and action height in both consumers, across three browsers and both locales/themes. Fractional height measurements were normalized to 1/64 CSS px after a retained floating-point comparison failure of about 0.000015 px; string-valued styles remain exact comparisons.
- PASS: 18 enlarged-text comparisons across both consumers and the design-system example found no fragmented action words, clipped paste placeholder or page overflow. Before/after desktop, mobile, enlarged-text and forced-color images were opened for review.
- NOT_RUN: physical camera hardware, operating-system clipboard permission dialogs on every platform and native mobile keyboard image delivery. Synthetic camera/clipboard failures and existing native desktop paste tests supplement these cases; they do not replace observed device evidence.

Revision readback used the Scanner's immutable footer source link and TOTP's source-revision meta element. Requests during these flows stayed GETs to the tool's own origin or blob URLs. Browser errors were absent. Live desktop/mobile and failure screenshots were opened.

PASS: 36 additional live enlarged-text cases covered both tools and [the shared design-system example](https://design.vinasig.io.vn/components/#qr-input-title), both locales/themes and three browsers. Action words stayed intact, placeholders were fully visible and pages had no horizontal overflow at 320 px and 200% text. Representative live enlarged images were opened.

The first live TOTP harness attempt tried to paste again after Clear all had closed the import disclosure. Its failure was retained. The harness now performs the real reopen action before a subsequent paste; no production assertion, control or source behavior was bypassed. These live checks use isolated synthetic clipboard/camera fixtures and a public RFC key, not owner credentials or actual device recordings. Device limitations listed above remain explicit.
